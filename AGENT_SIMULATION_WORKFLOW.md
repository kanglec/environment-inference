# AI agent workflow for DCFT simulations

## Purpose

This is the operating contract for an AI agent asked to produce simulation
results. The user should normally describe the scientific question, desired
accuracy, and any resource or timing limit. The agent owns the implementation
workflow: resolve the request into a campaign, deploy an exact source revision,
submit and monitor Bouchet work, retrieve verified results, analyze them, make
plots, and answer the question.

This is a research workflow, not a remote-computing product. Use the existing
`dcft` commands where they encode scientific or resumability invariants. Use
ordinary Git, SSH, Slurm, rsync, and Python for the surrounding operations; do
not add a new command merely to hide a short, inspectable research operation.

## Resolve the scientific request

Start from `configs/comparison.toml` for MC/ED agreement questions and from
`configs/scaling.toml` for large MC-only questions. Create a run-specific TOML
configuration and record every assumption that affects the scientific answer:

- lattice sizes, Euclidean-time factor, and regularization;
- Z or ZZ noise and the error-probability grid;
- measurement protocols and Gaussian fractions;
- posterior update method, including the TNMC bond dimension when used;
- outer-record and inner-chain budgets, diagnostics, and bootstrap budget;
- observable separations and whether ED is enabled.

Prefer a short clarification only when different choices would answer different
scientific questions. Otherwise choose a conservative pilot configuration,
state the assumptions, and proceed. Never silently turn a requested exact
calculation into a sampled fallback or reduce statistical budgets after
submission.

Give every run a unique, readable campaign ID, for example
`20260813-tnmc-homodyne-l16-32-a1`. Use it in both durable output and scratch
paths. Do not reuse an existing output root for a different scientific request.
The plan intentionally refuses such reuse.

Campaign TOML files are inputs, not compiled source. Changing a configuration,
README, tests, or this runbook must not change the runtime/source digest. The
runtime digest covers the Python/Rust implementation, build metadata, toolchain
pins, and dependency locks. The plan's configuration digest covers the
scientific request but excludes storage paths and Slurm shape. Consequently an
agent may tune Slurm resources without changing the scientific identity or
rebuilding an otherwise identical runtime.

## Shape the Slurm work

The current independent unit of MC work is one lattice/noise/probability/
protocol/update point. Tune its Slurm shape with these `[cluster]` fields:

- `time_limit`: wall-time limit for each task;
- `memory`: memory per CPU;
- `cpus_per_task`: CPUs assigned to one task;
- `max_array_concurrency`: maximum simultaneously running elements of each
  Slurm array.

The maintained MC kernels are currently operated as one-CPU tasks. Keep
`cpus_per_task = 1` unless a benchmark demonstrates useful parallel scaling for
the selected workload. Use array concurrency, not extra idle CPUs per task, to
increase throughput.

Before submission, run `dcft campaign plan` and count clean, exact, and MC
tasks. The exact array may overlap first with clean and later with MC. A
conservative peak estimate is

```text
peak array tasks = min(exact tasks, cap)
                 + max(min(clean tasks, cap), min(MC tasks, cap))
peak CPUs        = peak array tasks * cpus_per_task
```

where `cap` is `max_array_concurrency`. Singleton environment, analysis, and
validation stages run outside those array overlaps. Select the cap so the peak
respects the user's resource limit, including other active jobs managed in the
same task. If the user lifts the limit, raise the cap after checking account
policy and the 256-CPU consent boundary. If a single
task is unlikely to fit the `day` wall-time, first run a representative pilot
and inspect `sacct` elapsed time and maximum RSS; do not solve that uncertainty
by submitting the full matrix.

`dcft cluster render` places the cap in both the static array directive and
resumed subset submissions. Inspect the rendered DAG and scripts before the
first submission of a materially new campaign shape.

## Prepare an exact release

Work from a clean local `simulation/` Git repository. Verify tests in
proportion to the change, commit intentionally, push `main`, and record the
full commit SHA. A run-specific configuration may be committed for
reproducibility; configuration-only commits reuse an existing runtime when the
implementation and locks are unchanged.

On Bouchet, use a commit-specific durable checkout under

```text
/home/kc2254/project_pi_mc2832/kc2254/environment-inference/releases/<commit>
```

Clone from GitHub, detach at the exact commit, verify `HEAD`, require a clean
status, and then make the release read-only. If the directory already exists,
verify it instead of overwriting it. The campaign's `project_root` must resolve
to this checkout.

The controller environment belongs in commit-keyed scratch, not in the release
and not in a production task directory. Create it in a small Slurm controller
job. For a read-only checkout, the tested installation sequence is:

```text
uv sync --frozen --no-dev --no-install-project
uv pip install --python <controller-venv>/bin/python --no-deps --reinstall <release>
```

Set `UV_PROJECT_ENVIRONMENT` and `CARGO_TARGET_DIR` to commit-keyed scratch
locations. Then use that controller's `dcft` to run, in order:

```text
dcft cluster doctor --config <config>
dcft campaign plan --config <config>
dcft cluster render --config <config>
dcft cluster submit --config <config>
```

Capture the submit JSON, including every stage job ID, in the durable campaign
control directory and in the agent's working notes. Production tasks depend on
one source-digest-keyed environment stage. That stage may build a runtime once;
clean, MC, ED, analysis, and validation tasks must only reuse it.

## Monitor and recover

Monitor the entire submitted DAG, not only the validation/root job. Use
`squeue` while jobs are active and `sacct` for terminal state, exit code,
elapsed time, and maximum RSS. Read the stage log and `state.json` when any job
fails or is cancelled by dependency.

Do not blindly resubmit. Classify the failure first:

- transient scheduler/node failure: resume the incomplete tasks;
- environment or deployment failure: fix the release/runtime boundary, then
  resume;
- wall-time or memory failure: tune the Slurm shape and resume with the same
  scientific request;
- numerical, validation, or scientific failure: preserve the evidence and do
  not promote or answer from the run as though it succeeded.

After correcting a recoverable failure, use
`dcft cluster resume --config <config>`. Completion requires a successful
validation stage, all planned tasks complete, checksum-valid source-current
artifacts, and a final resume result of `nothing-to-resume`.

## Retrieve and analyze results

Results are durable under the campaign output root. Download through the SSH
alias `yale-bouchet-transfer` with resumable rsync, for example:

```text
rsync -aP --partial yale-bouchet-transfer:<remote-output>/ <local-result>/
```

Repeat the command if interrupted. After transfer, run `dcft inspect` and
verify every state-referenced artifact checksum locally. Confirm that artifact
source digests match the local implementation used for analysis.

The cluster DAG already produces maintained analysis artifacts, validation,
and standard witness plots. Start every interpretation from:

- the validation report;
- analysis diagnostics, including autocorrelation, replicated-chain behavior,
  inner-budget bias, and TNMC regularization counts;
- the scalar/curve or MC/ED comparison artifact relevant to the question.

For a follow-up question not covered by the standard plots, read the immutable
Parquet artifacts with PyArrow and write a small local analysis script or
notebook. Preserve paired outer IDs and complete curves in resampling. Do not
replace bootstrap intervals with independent pointwise calculations or report
the exploratory finite-size fit as a final exponent. Save derived plots with a
short record of their source artifact IDs and analysis choices.

## Report to the user

Lead with the scientific answer, not the mechanics. Include only the provenance
needed to judge it:

- campaign ID and exact Git commit;
- essential parameter choices and budgets;
- validation and diagnostic status;
- estimate, uncertainty, and any quadrature or finite-inner systematic;
- links to the most useful plots or local result files;
- limitations that materially affect the conclusion.

Do not claim a result from a pending, failed, stale, or unvalidated campaign.
Do not hide a sampled fallback, regularized TNMC conditional, poor mixing,
large inner-bias envelope, or inadequate finite-size range.
